# HomeClaim Runtime Readiness Inventory

Snapshot: 2026-10-18, after adding confirmation-gated same-world plot transfers.

This document records the observed code and runtime wiring. It is not a feature promise. A class, schema, or test alone does not make a user-facing function active. Re-check the current runtime path before relying on this snapshot.

## Status vocabulary

- `IMPLEMENTED_AND_ACTIVE`: registered in the current runtime and has a user or server entry point.
- `IMPLEMENTED_BUT_PARTIAL`: active, with known behavior or recovery gaps.
- `IMPLEMENTED_BUT_NOT_WIRED`: implementation exists but the current runtime has no entry point to it.
- `LEGACY_ONLY`: retained for source/data compatibility, not the canonical active path.
- `PLACEHOLDER`: a model, key, stub, or declared route without working product behavior.
- `DEAD_CODE`: no current callers or registration were found; remove only after checking compatibility.
- `MISSING_BUT_REQUIRED_FOR_EXISTING_FEATURE`: required behavior for an already exposed function is absent or unsafe.

## Runtime and user-function inventory

| Function | Status | Observed runtime behavior and limits |
|---|---|---|
| Paper bootstrap and command registration | `IMPLEMENTED_AND_ACTIVE` | `paper-plugin.yml` names `HomeClaimPaperPluginBootstrap`; Paper `LifecycleEvents.COMMANDS` registers Brigadier trees for `/homeclaim` (`/hc`), `/plot` (`/p`), and `/zone` (`/z`). Runtime services still initialize in the `JavaPlugin` lifecycle. |
| First-start config and database | `IMPLEMENTED_AND_ACTIVE` | `config/HomeClaim.toml` is created from defaults; SQLite is the default. Flyway initializes the common baseline, typed plot-home and backup metadata migrations, plus mutation-job diagnostic details. REST and ClientLink default to disabled. Startup fails when required storage initialization cannot safely complete. |
| World UUID binding and Area/Region persistence | `IMPLEMENTED_AND_ACTIVE` | The database is canonical. Paper worlds bind by UUID, with a legacy-name fallback before binding. Area resolution and region/zone persistence use the World/Area model. User-facing Area administration is not exposed as a dedicated command tree. |
| Plot-world setup and initialization | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | `/homeclaim setup` starts the player wizard; `/homeclaim plot init` and recovery initialize configured plots. New plot worlds use the native generator. Converting an existing world requires optional FAWE. Before conversion, the wizard now waits for all players in that world to confirm their asynchronous evacuation; a rejected or failed teleport aborts conversion and reports the affected player names. Admin setup completion callbacks return to Paper's server thread. |
| Claim | `IMPLEMENTED_AND_ACTIVE` | `/plot claim` resolves the current plot and uses `RegionOperationLimitService`, checks Area ownership/scope, persists owner state, and emits operation audit. Claims have a zero purchase cost in the active command path. There is no REST or GUI claim route. |
| Auto-claim | `IMPLEMENTED_AND_ACTIVE` | `/plot auto` chooses the nearest unclaimed region within the Area resolved at the player's position. It no longer mixes regions from another Area in the same world. |
| Merge | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | `/plot merge [direction]` validates same-Area adjacency, owner, and configured limits, reserves every affected region through the shared mutation conflict coordinator, and journals a correlated mutation job. It waits for Paper border/corridor painting before persisting the merge group and reporting success. A world failure leaves the group unmerged and marks recovery required. A later DB failure triggers best-effort visual compensation; compensation failure is also recorded as recovery required. No durable block-level undo exists. |
| Unlink | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | `/plot unlink [restoreRoads]` reserves the complete Area-scoped merge group, journals a correlated operation, persists the unlinked region state, waits for the Paper mutation future, and reports success only after painting. On failure it best-effort restores the merge group and merged visuals. If either compensation fails, the job is marked `RECOVERY_REQUIRED`; a crash while the job is nonterminal is detected at next startup. Partial block changes cannot be automatically reconstructed. |
| Reset | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | `/plot reset` creates an actor-, target-, state-, expiry-, and correlation-bound confirmation; `/plot reset confirm` or `/plot confirm` rechecks the current plot and access. The shared region mutation coordinator reserves the target. A versioned persistent pre-reset backup must reach READY before the queued batched Paper reset can mutate blocks. Reset progress is journaled and correlated. Partial mutation, cancellation after mutation, backend failure, or journal-finalization failure remains recovery work; there is no automatic resume or block-level undo. |
| Plot backups and restore | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | `/plot backup list` lists the latest ten ready backups and shows format, codec, stored/raw size, capture mode/timestamps, observed capabilities, and a checksum prefix when the manifest is readable. New backups use HCBK v3 with configurable `homeclaim.backup.compression` (`zstd` by default, or `none`); v1/NONE and v2/NONE-or-ZSTD remain readable. SHA-256 covers stored payload bytes (compressed bytes for ZSTD, raw bytes for NONE); capture metadata is bounded manifest metadata and is not part of that payload digest. `/plot restore <backup-id>` confirms and restores only to the exact original Region, Area, HomeClaim WorldId, Paper world UUID, and X/Z bounds. Before a restore writes any target block, it captures and checksum-validates a `restore_safety` snapshot and persists its BackupId in the restore job; a partial restore can be explicitly recovered from that pre-restore state. File IO, compression, decompression and validation run on the worker; capture/apply runs in bounded batches on Paper's server thread. Decompression is bounded by the HCBK payload limit and the manifest's exact raw length. This is a supported-content plot snapshot, not a full-world backup: block material/BlockData and supported container slot contents are captured. Non-container TileState causes backup failure before reset/restore. Biomes, entities, scheduled ticks and other non-container tile metadata are not encoded. Capture is explicitly tickwise and is not an atomic world snapshot. |
| Plot copy, move and swap | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | `/plot copy <target-region-uuid>`, `/plot move <target-region-uuid>`, and `/plot swap <target-region-uuid>` use the plot where the actor stands as the source/first target. Each requires `/plot confirm`; confirmation rechecks both region states, ownership/admin rights, Area/World bindings, bounds, merge state, and component presence. Transfers are limited to two claimed, unmerged, non-overlapping plots with identical bounds dimensions in the same Area and bound Paper world. Both snapshots must be READY and checksum-validated before mutation. COPY changes target blocks and supported container contents; MOVE verifies target before clearing source; SWAP captures both originals before writing either side. Ownership, roles, policies, limits, homes, prices, ratings, entry-denies, and components remain attached to their regions; plots with Components are rejected. Snapshots remain tick-wise/non-atomic and exclude entities, biomes, scheduled ticks, and unsupported tile metadata. Partial mutation is `RECOVERY_REQUIRED`; no automatic resume or rollback occurs. An operator can request confirmed `restore-target` for COPY or `restore-both` for MOVE/SWAP to reapply the recorded original safety snapshots. |
| Mutation job restart and recovery | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | Startup classifies durable queued work as `FAILED` (never entered execution), durable pre-write phases as `FAILED`, world-write phases as `RECOVERY_REQUIRED`, and interrupted operator recovery as `RECOVERY_REQUIRED`. Recovery-required and recovery-in-progress jobs continue to block destructive operations by RegionId after restart. `/plot jobs inspect <id>` is read-only. Operators with `homeclaim.admin.jobs.recover` can request confirmed `restore-target` for transfer/reset/restore jobs with a valid recorded backup, or `restore-both` for MOVE/SWAP. `/plot jobs resolve <id> acknowledge` requires `homeclaim.admin.jobs.resolve` and confirmation; it clears the block only after recording that the operator manually inspected/repaired the world. Acknowledgement is not a HomeClaim world repair or verification. Recovery writes ordinary child RESTORE jobs and retains the original job as `RECOVERED`; failed/partial recovery leaves the original blocked. No generic retry/resume, block-level undo, or automatic recovery exists. |
| Reset status, progress, cancellation | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | Reset journals a pre-reset backup ID, original world binding, and phase before world mutation. `BACKING_UP` is safely classified as pre-write; `RESETTING` remains blocked for explicit recovery after interruption. A valid linked pre-reset backup can be reapplied with confirmed `restore-target`. Restore jobs now also persist the ready, validated pre-restore safety BackupId; a partial restore can use the same confirmed recovery action to return to its pre-restore state. Older restore jobs without this safety reference retain their historical ability to reapply the requested snapshot, but cannot roll back to a pre-restore state. |
| Home, visit, teleport | `IMPLEMENTED_BUT_PARTIAL` | `/plot sethome` stores typed coordinates and orientation against the current claimed logical plot, without duplicating a world name. In a merge group the selected region is the explicit home anchor; the home may lie in any member region, and conflicting old homes are cleared on merge rather than selected by list order. Unlink clears an anchor that no longer contains its home. `/plot home [number|plot-id]` uses a valid stored home, otherwise its existing deterministic safe center fallback. A stale/ambiguous home is rejected and logged before teleport. `/plot visit` keeps the center fallback. Paper World/Area resolution prefers UUID binding and teleport success remains asynchronous. |
| Delete / unclaim confirmation | `IMPLEMENTED_AND_ACTIVE` | `/plot delete` (`/plot unclaim`) creates an actor-, operation-, target-, state-, expiry-, and correlation-bound pending confirmation. `/plot confirm` re-resolves the region and signature, rejects a pending delete if an active or recovery-required mutation now affects it, consumes the pending entry exactly once, then calls the actor-aware `RegionUnclaimService` while holding a short unclaim reservation. Merged regions are rejected until `/plot unlink` completes. Delete releases ownership without a physical reset; it clears roles, home, alias, description, and listing price, while retaining the physical region, local policy/limits, components, ratings, and entry-deny rules. |
| Plot biome | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | `/plot biome <biome>` resolves current biome keys through Paper's registry and validates owner/admin state in `RegionBiomeService`. It reserves every selected logical plot/merge-group member, journals the bounded Paper tick-batch mutation, and writes one terminal correlated audit result only after completion. The existing block mutation backend cannot express biome cells, so the Paper biome writer is a bounded platform mutation adapter. A partial failure is `RECOVERY_REQUIRED`; its progress is diagnostic only and there is no persistent biome rollback or resume. |
| Plot info and list | `IMPLEMENTED_AND_ACTIVE` | `/plot info` and `/plot list` read region, role, flags, price, rating summary, and owner presentation. Display falls back to the legacy world-name field if no Area/World record is available; info still computes its displayed build summary directly from role state. List does not teleport to a selected region. |
| Merge group filtering | `IMPLEMENTED_AND_ACTIVE` | Active merge and unlink candidate/group selection now uses `AreaId` rather than the deprecated world-name field. World mutation backends still use Paper world names at their platform boundary. |
| Roles and membership | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | `RegionRoles` resolved by the policy path is the only runtime membership state. `RegionRoleService.mutateRole` owns actor authorization, target/owner/self-ban validation, idempotent add/remove behavior, persistence/runtime update, `OperationResult`, and correlated audit. GUI, REST, and `/plot add|trust|deny|remove <online-player>` call that service. Command target resolution is intentionally online-only and never derives UUIDs from names. `/plot remove` only removes explicit MEMBER/TRUSTED/BANNED assignments. |
| Entry-deny and force-entry | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | Entry policies consume role and cached entry-deny state. REST create/report/revoke call `EntryDenyOperationService`, which validates scope/reason/expiry, authorizes through the shared mutation authorizer, returns `OperationResult`, and audits the authenticated `SYSTEM` actor with request correlation. The pre-release `created_by` column is nullable, so system-originated entry-deny changes no longer persist an all-zero fake player UUID; client actor UUID fields remain ignored for compatibility. `/homeclaim entryforce` remains a separate admin path. Ejection is called only after successful create; callback failures are logged without turning a persisted create into an HTTP failure. |
| Flags, limits, and profiles | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | `RegionAdminService` actor-aware operations validate catalog keys/types, support flag/limit inheritance by clearing the local override, preserve `-1` as unlimited, apply profiles, update the region/profile runtime snapshots, return `OperationResult`, and write correlated audit. In addition to the established build/interact flags, active Paper handlers now have distinct `PISTON`, `LIQUID_FLOW`, `HOPPER_TRANSFER`, `DISPENSER`, `PROJECTILE`, `HANGING_ENTITY`, `ITEM_DROP`, and `ITEM_PICKUP` flags. GUI flag edits expose a compact subset; REST/profile/config paths can use every catalog key. Zone `lockedFlags` precedence remains in the central policy resolver; editing a region flag cannot override a locked zone rule. Limits/profile editing is REST-only; no such GUI editor is registered. |
| Plot manager GUI | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | `/plot gui` and `/plot menu` open the owner's region list; the manager routes to role, price, flags, components, and zone information through the registered GUI event listener. Role add/remove, flag change, price change, component create/update/remove use shared actor-aware operations and show failure feedback. The role selector is intentionally online-only. This pass did not have a connected client, so live inventory click behavior remains unverified. |
| GUI price editing | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | Price edits now use `RegionAdminService.setPrice`, which checks owner/admin capability, validates finite nonnegative values, persists, updates the region runtime state, and audits before success feedback. This is only listing-price metadata; no buy/sell transaction is connected. |
| Components | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | Elevator and teleport pads persist through the runtime snapshot and are resolved by typed component resource for protection/LiftLink. Active GUI create/update/remove paths use `ComponentOperationService` for region/scope validation, creator attribution, authorization, result handling, runtime visibility, and correlated audit. The JDBC repository requires and stores the creating player. REST currently exposes component reads only. Core's `ComponentTypeRegistry.runtimeSupport` distinguishes the two enum-backed runtime types from descriptor-only custom names; core/client registries do not install persistence, operation dispatch, or Paper handlers. The unregistered `BukkitComponentCreationService` and its independent in-memory menus were removed so no second component-mutation path remains. |
| LiftLink | `IMPLEMENTED_AND_ACTIVE` / `IMPLEMENTED_BUT_PARTIAL` | `PaperPlatformBridge` registers `PaperLiftLinkListener`; `ComponentTriggerHandler` and `LiftLinkPlanner` resolve enabled elevator/teleport pads and check component use. Same-world and cross-world teleports are supported, with explicit `homeclaim.elevator.crossworld` permission for cross-world pads. Completion feedback and terminal audit follow the asynchronous teleport result. The additional world-restriction method was removed because it always allowed travel; no separate world deny policy exists. |
| Spawner use and drop protection | `PLACEHOLDER` | `SPAWNER_USE` and `SPAWNER_TAKE_DROPS` action identifiers exist, but no active Paper spawner handler was found. Do not describe these actions as protected behavior. |

## Registered protection coverage

The following is a source-and-test inventory of the listener groups registered by `PaperPlatformBridge`. `SUPPORTED` means a registered Paper event is translated to an active `ActionKey` and policy decision; it does not promise coverage of every mod or plugin side effect.

| Scope | Status | Registered handling and policy boundary |
|---|---|---|
| Block placement, break, interaction, containers | `SUPPORTED` | `BlockPlaceEvent`, `BlockMultiPlaceEvent`, `BlockBreakEvent`, and `PlayerInteractEvent` use BUILD, BREAK, INTERACT_BLOCK, or INTERACT_CONTAINER at the target. |
| Buckets, sponge, liquid flow | `SUPPORTED` | Bucket source/target, `BlockFromToEvent`, and `SpongeAbsorbEvent` use LIQUID_FLOW. Cross-boundary source and target are evaluated; sponge retains only allowed targets. |
| Pistons | `SUPPORTED` | Extend/retract evaluate every moved block's source and destination with one correlation; any denied pair cancels the Paper event. |
| Hoppers and inventory transfer | `SUPPORTED` / `PARTIAL` | `InventoryMoveItemEvent` uses HOPPER_TRANSFER. When both inventories resolve to positions, source and destination are evaluated together. When only one resolves, that actual position is checked with the missing endpoint recorded as positionless; no synthetic location is created. If both endpoints are positionless (for example virtual/plugin inventories), the event has no spatial HomeClaim scope and is left to the inventory owner/plugin. |
| Dispensers and droppers | `PARTIAL` | `BlockDispenseEvent` and armor dispense evaluate dispenser source and facing/entity target. Later block/entity effects remain subject to their own Paper events. |
| Fire, growth, physics, falling blocks, redstone | `SUPPORTED` / `PARTIAL` | Ignite, burn, spread, form/grow, fertilize, structure growth, physics, falling-block changes, and redstone transitions are registered. Some vanilla follow-up effects are necessarily represented by later Paper events. |
| Explosions | `SUPPORTED` | Entity and block explosions bulk-evaluate every affected block and remove denied targets from Paper's block list using one correlated audit result. |
| Entity, hanging, vehicle, item interactions | `SUPPORTED` / `PARTIAL` | Damage, entity interaction, armor stands, hanging placement/break, leash, shear, entity placement, vehicles, item drop/pickup, and inventory pickup are registered. Villager, animal, and tamed-entity interaction use the common entity-interaction action rather than separate flags. |
| Projectiles | `PARTIAL` | Launch retains shooter/dispenser/system cause and source/target; entity impacts and projectile-caused explosions use later damage/explosion events. Projectile-caused ignition uses the existing REGION_FIRE decision and now attributes the shooter (including dispenser automation) and causal source when Paper exposes them. A generic projectile block-hit event is not converted into a broad interaction action; effects without a later, unambiguous protection event remain outside generic projectile-hit coverage. |
| Movement and entry deny | `SUPPORTED` | Player movement/teleport entry, vehicle movement, and controllable mounts compare boundaries and apply entry/vehicle policy. |
| Portals | `SUPPORTED` / `PARTIAL` | `PortalCreateEvent` checks every resulting portal block through the bulk REGION_BUILD/BUILD policy; any denied managed target cancels the whole atomic portal-creation event. No additional portal flag was added. Player portal travel is handled by the existing `PlayerTeleportEvent` path and therefore retains target entry-deny and teleport policy. Non-player `EntityPortalEvent` travel is not independently constrained because HomeClaim has no general entity-entry policy. |
| Spawner use and drops | `NOT_SUPPORTED` | `SPAWNER_USE` and `SPAWNER_TAKE_DROPS` remain identifiers only; no registered Paper handler claims protection support. |

Known adapter shortcuts remain: REST uses one server admin-token actor rather than per-user principals, and the role GUI deliberately limits new assignments to online Paper players because no authoritative offline identity resolver is configured. Actorless role and administrative mutation adapters, the unused direct `JdbcRoleRepository`, and the unconnected PlotMember service/repository were removed. `PolicyActionRequest` and the unregistered Bukkit import/command executor adapters were removed. `Decision.allowed` and its Boolean constructor were removed because there was no current internal caller or published core API contract; active policy, protection, REST mapping, and tests use `DecisionEffect`. Selected string-world DTO/config/platform fields remain explicit compatibility boundaries.

`PendingConfirmationStore` is a small volatile, actor/operation/target/state-bound primitive used by `/plot delete`, `/plot reset`, `/plot restore`, and the plot transfer commands. It preserves a pending request on a wrong operation/target/state consume attempt, removes expired entries, and consumes a matching request once. It is deliberately not a durable workflow or resume mechanism.

## Step 14B HTTP and runtime verification (2026-10-18)

The preference is Zstandard, then Brotli, then identity; known-length responses below 1 KiB remain raw. Unknown-length serialized/streaming text responses are eligible for compression because Ktor has not materialized a length at the negotiation point; this means a small unknown-length API object can also be compressed. Compressible media types are text, JSON, JavaScript, XML and form data. Zstandard uses `zstd-jni` level 3. Brotli uses Brotli4j quality 4. Responses with an existing Content-Encoding are not recompressed. No gzip encoder is registered.

Last-Modified/If-Modified-Since and If-None-Match are supported. Byte ranges are deliberately not served (`Accept-Ranges: none`; Range is ignored and receives a full representation).

## Step 20B destructive database outage / process recovery (2026-10-24)

- The active destructive mutation paths already persist write-ahead phases before changing blocks: RESET uses `RESETTING`; COPY/MOVE/SWAP persist `APPLYING_TARGET` and subsequent phase intent before the corresponding write; RESTORE persists `RESTORING` after its safety backup; Merge/Unlink persist `WORLD_MUTATION` before painting. Startup treats a durable job interrupted in one of these phases conservatively as `RECOVERY_REQUIRED`. This is phase evidence that a write may have started, not proof that it completed.
- The full-Paper outage harness holds a test-only barrier after a controlled partial COPY worldwrite (100 block writes), stops the real database container, and checks that the source is unchanged, the target is partial, success is not reported, and affected regions remain blocked. The barrier and fault injector live only in the `paperWorldE2E` companion artifact.
- **PostgreSQL 17.11 / Paper 26.3 build 218:** the same Paper process verified the pre-worldwrite outage and pool recovery; after the partial COPY outage it exited without recording success. A second Paper process opened the same persistent database and world, classified the durable `APPLYING_TARGET` job as interrupted/recovery-required, restored the target from its ZSTD safety backup, verified source and target snapshots, and cleared the blocker. Result: `PASS destructive DB outage partial COPY recovered after Paper process restart with DB returned`.
- **MariaDB 11.4.13 / Paper 26.3 build 218:** the real Paper process verified the pre-worldwrite outage, restored the database without plugin restart, then injected a partial COPY, lost the database, rejected successful completion, reclassified the persisted phase after reconnect, and explicitly ran `restore-target`. Result: `PASS destructive DB outage after partial COPY write; durable APPLYING_TARGET reclassified; same-Paper reconnect and explicit restore-target recovery`.
- The first MariaDB run exposed that unqualified `TIMESTAMP` columns discarded the millisecond precision stored in HCBK backup manifests, causing provenance validation to reject a valid backup. The canonical pre-release V3 backup schema now uses `TIMESTAMP(3)` for `created_at` and `ready_at`; fresh PostgreSQL and MariaDB initialization and destructive recovery scenarios passed afterward. Existing already-created pre-release development databases may need recreation under the repository's pre-release migration policy; this is not a post-release upgrade instruction.
- While the DB is unavailable, HomeClaim cannot durably write a new terminal status or audit row. Transfer failure journaling therefore runs off the Paper tick while retaining its in-memory reservation; the previously persisted write-ahead phase remains the durable restart evidence. Recovery and its audit are written after database return. If the process terminates while the DB is down, startup uses the persisted intent and conservatively requires explicit operator recovery. No guarantee is made that the outage itself can persist a new status or audit.
